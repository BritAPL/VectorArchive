<p>Exploring ActiveX Data Objects from Dyalog APL by J. Korablev and G. Roche (Gunter.Roche@gmx.de)</p>
<p>Abstract This paper presents a short overview of the ActiveX Data Objects (ADO) model and the main steps for application development in Dyalog APL. ADO wascreated by Microsoft in order to provide an easy-to-use application level interface to currently known data sources. This interface is based on the underlying system service OLE DB andis used in tools for rapid application development. ADO is easily accessible for users, becauseit is included with popular Microsoft products such as Internet Explorer 4.0, Internet Information Server 4.0 etc. ADO is also available for download from the Microsoft Web site (the OLE DB SDK, the Microsoft Data Access Components 2.0, and the Data Access SDK). The implementation of ADO in Dyalog APL is based upon OLE Automation, a mechanism thatallows one application to control another, and which provides the ability to mix code written in different programming languages.</p>
<p>Introduction. OLE DB and ADOarethe low andhighlevels of interface that enable Universal Data Access. This is Microsoft strategy for providing access to all types of information from a variety of data sources (relational and non-relational data, mainframe ISAM/VSAM, hierarchical databases, emails and file system, text, graphical, and more). For each kind of the data source there is a specific service component, called a provider. An integral part of OLE DB is the OLE DB Provider for ODBC, which enables OLE DB to communicate with today s popular ODBC drivers and data sources.</p>
<p>There is a definite difference between ADO and OLE DB from the developers point of view, OLE DBenables universal access to any data. ADOfacilitates it for developers of programs. Since ADO is located on top of OLE DB,it has a low memory overhead, and a small disk footprint. ADO supports key features for building client/server and Web-basedapplications, includingthe following:</p>
<p>* Independently-created objects. This allows the programmer to create and work only with the objects that are required.</p>

<p>* Improved performance by updatingall data on the server in a single update (Batch Updating).</p>
<p>* Support for stored procedures.</p>
<p>¢ Different cursor types.</p>
<p>* Automatic or manual parameters managementfor better performance and morecontrol.</p>
<p>ADOis implemented as an OLE Automation Server andis accessed from Dyalog APL using the OLEClient object. Note that OLE is very dependent on the Visual Basic programming language and APL syntax is more restricted than Visual Basic. This discussion of the ADO object model aims to cover the main steps involvedin application development with Dyalog APL.</p>

<p>The Connection (drives a connection under a definite provider), Command (executes a command, such as a command text, stored procedure, command prepare etc.), and Recordset(a set of records returned by commands) objects are top-level objects that can be created and destroyed independently. They are</p>

<p>registered in the Windowsregistry as ADODB.Connection, ADODB.Command, and ADODB.Recordset, respectively.</p>
<p>In addition to these three top-level objects, there are four other subsidiary objects, that exist only within the context of their parent objects, and cannot be created separately, namely Parameter, Field, Error and Property.</p>
<p>The Parameter (ADODB.Parameter in the Windowsregistry) object can be created. independently of a Command object. In this case it must be included in a Parameters collection of a Commandbefore it is used in a command. Parameter objects can be created from the Parameters collection too, where they are placed automatically as a result of a statement syntax setting in a Command object. Calling its Execute method assigns corresponding Value properties to all Parameterobjects in the collection. It provides the facility to use bind variables in SQL expressions. The Field object provides structural information about a single column of data within a Recordset. The Error object supplies extended error information about an error condition generated by the provider. The Property object describes provider-defined characteristics of an ADO object.</p>
<p>Each of the Error, Property, Parameter and Field objects are accumulated in the corresponding collections: Errors, Properties, Parameters, and Fields. (A Collection is a special kind of object that contains a set of other objects; you can think ofit as a vectorof objects.)</p>
<p>There are two ways to access the properties and methods of ADO objects from Dyalog APL. If, when an instance of an ADO object is created as an OLEClient object, the AutoBrowse property is set to 1 (the default), the methods and the properties of this object appear as functions and variables in the OLEClient namespace. In principle, with a few exceptions, a method corresponds to an APL function and a property corresponds to an APLvariable. This is possible because ADO objects have a type-library file with type information, that includes the name of the methods and properties exported by the object, together with descriptions of the arguments to each method and descriptions of the data types of each property. An alternative, is to specify AutoBrowse as 0 when creating the OLEClient. This causes Dyalog APL to create an empty namespace whose methods are accessible using 3 UNQ and whose properties may be queried and set using OWG, OWS. This approach is faster, because APL does not have to read the object s type-library for the information it needs to establish functions and variables corresponding to the object s methods and properties. However, in practice it is much better/safer/more maintainable to leave AutoBrowseas 1.</p>

<p>Basic ADO Application Steps This section describes the general flow and the basic steps for developing ADO applications in Dyalog APL. Most such applications use some variation of the following steps:</p>
<p>* Connect to a data source by meansof a Connection object. Optionally, begin an explicit or implicit transaction.</p>
<p>* Optionally, create a Commandobject to represent an SQL command with or without parameters.</p>
<p>* Optionally, if a parameterized commandis involved, specify columns,tables, and values in the SQL commandasvariable parameters via the Parameter object.</p>
<p>« Execute the command.This can be carried out by the Command, Connection, or Recordset object. * After executing, a result is returned in a storage object Recordset.</p>
<p>* Optionally, view,sort, filter, and navigate the data in a Recordset.</p>
<p>* Edit, add, delete the data in a Recordset. Work directly with columns or rows via the Fields collection and Field objects. * Ifitis all right, update the data source with changesfrom the object Recordset.</p>
<p>* Ifa transaction was used, commit or rollback the changes made during the transaction. This is a function of the Connection object.</p>
<p>* Retrieve the providers information about each object via a Properties collection. Each collection contains a set of Property objects for a specific instanceof an object.</p>
<p>* Retrieve the information abouterrors during connection (Error objects via Errors collection).</p>

<p>Comparison between Different Approaches to Data Access Dyalog APL can choose from many of Microsoft's technologies for accessing data sources, These include:</p>
<p>* Open Database Connectivity (ODBC)forrelational data via the ODBC API code,</p>
<p>124</p>

<p>* Remote Data Objects (RDO) for ODBC data.</p>
<p>* Data Access Objects (DAC)for local data (Microsoft Jet database engine).</p>
<p>« DAOfor ODBC data (ODBCDirect).</p>
<p>* Microsoft ActiveX Data Objects (ADO)forall types of data.</p>
<p>All the above-mentioned object models (RDO, DAO, ODBCDirect, ADO) were invented to give developers the ability to avoid direct programming of the corresponding API. They are an artificial layer over this API, and provideall their functionality in an object modelof type easy-to-use , rather than in a collection of function calls ina DLL.</p>
<p>Today, there are features that are not available in ADO, but which are present in one of the alternative object technologies. However, the aim of ADO is to become a superset of DAO and RDO.</p>
<p>One of ADO s benefits here is the declaration of a simple and understandable languagefor accessing data. ADO nowplaysthe role of the standard data access language for Microsoft tools and program products. For example, the current versions of Internet Information Server, Internet Explorer, Visual Basic, Visual C++, and Visual J++ can use ADO as their primary data access and control language. The nextrelease of Microsoft Office promises to dothis too.</p>

<p>The use of ADO from Dyalog APL compared with the base ODBC API DLL shows on the one handa little more general performance of the DLL-approach, because of the usual benefit of compiled DLLs vs. interpreted Dyalog APL. On the other hand, the performanceof the base function calls in the DLL compared to the speed of the methods in ADO for connecting, query preparing, executing, fetching and closing is practically equal. Finally, ADO is more universal than the DLLs in offering functions, data types, and data sources. Additionally, ADO providesfull controlofall steps for data access in Dyalog APL.</p>

<p>Conclusions ADO provides the capability to carry out query and manipulation (SELECT, INSERT, UPDATE,and DELETEstatements) of all types of data. To access most popular telational data ADO can use OLE DBdirectly, or it can use the OLE DB Provider for ODBC. To access other types of data, there are other kinds of data providers.</p>
<p>Notall ADO features were discussed here, for example:</p>
<p>« Free threading, that allowsoneto build very powerful and scalable Web server applications.</p>
<p>* Asynchronous queries, that return controlto the application before the query is completed.</p>
<p>° Remote Recordsets, that allow one to retrieve and manipulate data remotely, then updatethe source.</p>
<p>* Events, that allow ADO 2.0 to exposea list of events that can be used to control all aspects of the connection, query, and table access process.</p>
<p>Since ADO is a COM-based component, called using the Automation interface, Dyalog APL can use ADO and combine high-performance access to any data source with its own capabilities of efficient array data processing.</p>
